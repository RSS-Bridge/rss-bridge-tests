Synaptics patent claims stop work on DisplayLink drivers

2026-11-12 00:00:00

by: Joe Brockmeier

By Joe Brockmeier

November 10, 2026

Mike Lothian owns a docking station (or dock) that uses a DisplayLink chipset that had, at least in his opinion, subpar performance on Linux. He decided to try improving the Linux driver, with LLM assistance, but ran into one problem that he could not solve—so he asked for help, hoping that Synaptics's developers would lend a hand. (DisplayLink was acquired by Synaptics in 2022.) Rather than help him in improving the driver, however, the Synaptics legal team responded with patent infringement claims, a demand that he cease unauthorized implementation of DisplayLink technology, and threats of expensive legal penalties. For now, it appears that Linux users of the company's docks will have to continue to live without feature parity with other platforms.

Synaptics and Displaylink

The dock that he was trying to support is a Dell device that connects to a system via USB 3 and allows users to connect multiple monitors and other devices to their computer. It provides its DisplayLink Manager (DLM) software for Linux for the devices via an APT repository for Ubuntu.

The company only provides DLM software in binary form, and only for x86-based platforms. The software is proprietary, but the company does maintain an open-source, out-of-tree kernel module that is included with DLM, the Extensible Virtual Display Interface (EVDI) project. It provides a driver that's compatible with Linux DRM and allows users to manage their docked displays with standard tools used for display settings, such as xrandr or GNOME and KDE Plasma's utilities.

A short article explains why the company has not released source code for DLM: the software uses a proprietary graphics technology called DL3 to create a compressed stream of the various channels (e.g., USB, DisplayLink video, audio) over a communication channel (USB 3 in this case) and decode it again for output to the user's devices.

Unfortunately, the vendor-supplied software did not work well for Lothian. I spoke and chatted with him via Signal while writing this article; he said that the driver kept crashing under Linux, so he decided to use his Claude subscription to try to develop a new driver and support software.

Vino

He posted the first patch series for Vino—his Rust-based DRM/KMS driver—to the kernel's dri-devel list as an RFC on June 17. Lothian noted that it was in an incomplete state, and asked for help with a blocker that he had run into trying to communicate with the dock's control plane. "If you have knowledge of the DisplayLink DL3 control-plane engagement sequence, or ideas for isolating a whole-bus timing/ordering property a per-channel diff cannot see, help would be very welcome." He received feedback from a few developers, including guidance from Danilo Krummrich to rework the driver to use the Rust KMS bindings, but no advice specific to the problem he was trying to solve.

Lothian also opened an issue on the EVDI GitHub repository on June 17. It explained the work he'd done so far, outlined the approach in trying to reverse-engineer the DL3 protocol, provided links to his GitHub repository with the Vino code, and asked for clarification on a few issues. There was no reply to his issue.

He also reached out to Łukasz Spintzyk of Synaptics directly by email; his correspondence with the company between July 5 and October 7 is available in this PDF compiled by Lothian. He noted that he had found a few bugs in EVDI and opened a pull request (that went unreviewed for several months), and also asked for assistance where he was blocked on Vino. On July 20, he received a reply, not from Spintzyk, but from Michal Lukaszek of Synaptics:

The reason I'm writing is that DisplayLink is not an open standard. The protocol, codec, and other technologies used by DisplayLink devices are proprietary to Synaptics and are protected by a substantial portfolio of patents in a number of jurisdictions, including the UK.

From what you've published, it appears that the VINO project is progressing beyond interoperability work and toward implementing technology that we believe is covered by those patents. While many developers understandably focus on avoiding copyrighted source code, patent law is different. An independently written or clean-room implementation does not necessarily avoid patent infringement if it implements patented inventions.

Lukaszek said it was entirely possible that Lothian was unaware of the "intellectual property landscape surrounding DisplayLink", so he wanted to make him aware now rather than "have the situation become more formal later". Lothian lives in Scotland and has a ".co.uk" email address, which explains why the email made reference to the UK.

Cease and desist

On August 17, Andrew Bateman, an assistant general council of intellectual property for Synaptics, sent a cease-and-desist notice. The letter stated that Lothian had not "substantially responded" to Lukaszek's communication, and had continued with "public statements and further development activities". It included an appendix with a list of 125 patents that "cover fundamental aspects of DisplayLink's architecture and operation", but did not specify which patents might be infringed by the work.

Synaptics included a list of eight demands it expected immediate compliance with, including ceasing development of "any software or other implementation that infringes any Synaptics patent", withdrawing submissions of materials "made to Linux kernel maintainers, mailing lists, code-hosting platforms, package maintainers, distributions, or any other person or organization", and to identify in writing every location "in which the relevant materials have been published, submitted, stored, or distributed". It also demanded that he provide Synaptics with a signed confirmation, by August 28, that he had complied with its demands.

Lothian, instead, posted version three of his Vino work for the DisplayLink docks to the dri-devel list on August 26. He said that the previous two versions had "never lit a panel", but the new work could control three generations of DL3 docks without any vendor software. There were no substantive reviews of the patch set posted to the list, though there were some automated reviews from Sashiko.

On August 27, Lothian responded to Bateman and asked him to elaborate on the patents that Synaptics thought were being infringed. "A claim chart mapping the relevant claims to the relevant code would make it much easier for me to understand and properly respond to your concerns."

He also expressed confusion about Synaptics's position that his work was being treated as patent infringement. Synaptics is a member of the Open Invention Network (OIN), which was created to help open-source developers and vendors deal with the threats of expensive patent litigation. It holds a large, cross-licensed portfolio that serves to provide patent protection to individuals, open-source projects, and large vendors alike. Lothian said that he was now an OIN licensee as well, and he thought that it was supposed to "reduce exactly this sort of patent problem around Linux and open source software".

He asked Bateman to explain how Synaptics claims "interact with our respective OIN commitments", and expressed a desire to sort things out with Synaptics constructively. "I don't think a public dispute between Synaptics and an individual open source developer would be particularly helpful for either of us, especially within the Linux and open source communities".

Lothian did not think he could "reasonably provide the signed undertaking" Synaptics had demanded by August 28 without understanding which patent claims it was alleging. He asked for an extension to the deadline. There was no response from Bateman, so Lothian sent a follow-up email on September 18. He said he was concerned there was no acknowledgment to his last email, and wondered it was safe to assume he could continue his work. He had been running the Vino driver himself for quite a while, and was eager to move it upstream without having patent threats hanging over the work.

Bateman responded the next day and said that he should be concerned:

As you previously requested, we have been documenting your ongoing patent infringement by mapping your Vino driver to specific claims of our DisplayLink patents. I will provide this claim mapping documentation to you within the next two weeks. I will also be sending to you our demand for substantial monetary compensation to recoup the cost and effort required to create such documentation of your infringing acts. I previously gave you the opportunity to stop your infringement, but you decided to push back and not heed my warnings, and so now we are escalating as we deem appropriate.

The letter continued to claim that Lothian would be "single-handedly eviscerating DisplayLink's competitive advantage in this crowded market by educating our competitors and other third parties as to how we implement our proprietary technology". He said that DisplayLink is not a member of OIN, and none of its technology is licensable through OIN or any other organization.

Bateman sent a follow-up letter, dated October 5, that included two claim charts for UK patents: GB2484736B ("Display control device") and GB2485613B ("Image generation"), both filed in 2010 and published in 2012. He reiterated Synaptics's demands from its previous letter, and said that the deadline was now October 11; failure to comply would result in the company seeking "monetary compensation from you in the amount of US$25,000 to recoup the costs and effort required to create the attached documentation of your infringing acts". That amount would be increased by $25,000 each week until the company's demands were complied with.

Lothian responded the next day, by email, to say that he was on vacation, and would not be back home until October 13. He asked for an extension of the deadline to return home and go through the claim charts "ideally with someone qualified to help me read them". Bateman replied that Synaptics would agree to extend the deadline to October 18, though no further extensions would be granted. He reiterated that "DisplayLink is not a member of OIN" and none of its technology was licensable through OIN.

OIN to the rescue?

Synaptics is a member of OIN, and is listed in the community directory. In addition to joining OIN, Lothian had reached out to the organization to try to solicit its help and has been in communication with some of the staff there. OIN indicated that it would look into the matter and see if he had any protection as an OIN member. That process took longer than Lothian hoped, though OIN did eventually provide its conclusion.

OIN's portfolio covers a wide range of software that matches its Linux System Definition, but it does not cover everything that might be implemented for a Linux system. In particular, its definition specifies that codecs ("a component of a program capable of performing transformations of a video, still image or audio data stream or signal") are not covered unless specifically mentioned in this list of components.

I spoke briefly to OIN CEO Keith Bergelt on October 23, shortly after OIN staff informed Lothian of the result of their research. Bergelt said that OIN's conclusion was that, since codecs are explicitly not covered by OIN's Linux System Definition, its protections did not extend to Lothian's attempted kernel contributions. OIN had recommended that Lothian reach out to a lawyer in the UK, and provided a recommendation.

Status

Unfortunately, that referral did not pan out, Lothian said. He has not given up entirely, but he has taken down the GitHub repository to comply with Synaptics's demands. For now, he may continue working on some of the components that are not affected by the patent claims, but the work on Vino will not be submitted to the kernel. "Vino itself has to remain local until this is sorted out, I just can't afford to defend myself against Synaptics."

Perhaps amusingly, Lothian told me that someone from Synaptics finally replied to the pull request on October 7. Lothian told me he does not intend to follow up on the comments: "You can't threaten to sue me and then say 'can you update your pull request?'"

For the time being, Synaptics has succeeded in shutting down an effort to improve the way DisplayLink docks work with Linux. It is an unpleasant reminder that, while much of the current conversations in open-source communities are concerned with LLM-driven development, software patents still pose problems for free-software developers and users.

Git considers voting to determine its LLM policy

2026-11-12 00:00:00

by: Jonathan Corbet

By Jonathan Corbet

November 9, 2026
One of the dominant themes of 2026 has been the debate within development projects about the terms under which LLM-written contributions should be accepted — if, indeed, they should be accepted at all. The Git project has not been immune to this trend; the topic was discussed at the recent Git Contributor's Summit. In this case, the path to a resolution may be somewhat circuitous; the project, which has never been governed as a democracy, is considering adopting a voting process as a way of bringing the discussion to an acceptable conclusion.

Like most projects, the Git community has been considering its policy toward LLM-written contributions for a while. In October 2025, the project updated its SubmittingPatches document to include this policy:

The Developer's Certificate of Origin requires contributors to certify that they know the origin of their contributions to the project and that they have the right to submit it under the project's license. It's not yet clear that this can be legally satisfied when submitting significant amount of content that has been generated by AI tools.

Another issue with AI generated content is that AIs still often hallucinate or just produce bad code, commit messages, documentation or output, even when you point out their mistakes.

To avoid these issues, we will reject anything that looks AI generated, that sounds overly formal or bloated, that looks like AI slop, that looks good on the surface but makes no sense, or that senders don't understand or cannot explain.

This policy was reconsidered at the Contributors Summit, but without any clear conclusion. Some participants seem to be open to relaxing the policy, while others raised the ongoing copyright concerns or worries that accepting LLM-written contributions will erode some people's trust in the project. About the only consensus that, seemingly, was reached was that it would not be possible to come to a consensus on the topic.

The idea of putting the question to a vote was raised in that same session, and Emily Shaffer agreed to take on the task of creating a process within which such a vote could be held. A draft version of that process was posted for consideration on October 21.

The voting proposal seems to be somewhat influenced by Debian's process, but it is not exactly the same. When the time comes to vote on a topic (the determination of that time is left to the Git maintainer), proposals are to be formatted as patches to the project's documentation. Each proposal would be posted and discussed individually, with the intent of polishing it, rather than transforming it into something substantially different. Anybody who is eligible to vote (eligibility is discussed later) can put forward a proposal; any given proposal will only be added to the ballot if it is seconded by another eligible voter.

The discussion period is expected to last "around 4 weeks" as the proposals are reworked into their final form. At the end of that period, the proposals will be collected into a ballot, and voting will take place over a two-week period. The proposal says nothing about how the votes will be counted — whether the proposal with the most direct votes wins, or whether some sort of ranked-choice process will be used.

Eligibility to vote, as described in the proposal, would be:

Votes are welcome from contributors who have authored a commit which has been merged to next, or who have provided 2 or more code reviews, and who have not been banned from participation in the project.

As was pointed out in the ensuing discussion, that was a rather more inclusive set of criteria than was discussed at the Summit, where a requirement of at least 50 commits in the Git history was tossed out. There was no real agreement on what the correct threshold should be; Patrick Steinhardt suggested that a commit count of 25 or 30 might make sense, Jeff King proposed a more complex rule that gives some weight to longer-term contributors, and brian m. carlson just wanted a threshold "where people are not incentivized to contribute only to vote". Fortunately, nobody suggested setting up a process to vote on that question.

Kristoffer Haugsbakk claimed that the vote process would lead to a foreordained conclusion for the issue at hand:

The vote will pass. Those who work on Git at least once a month work for tech companies. Those tech companies are now AI companies. The votes will happen to drift towards agreement with their management.

That led to objections from developers like Steinhardt and carlson, who insisted that they would vote based on their own conclusions rather than those of their employers. They both agreed, though, that the voting process should be secret so that employers could not force their developers to vote a certain way.

The conversation has slowed down without any firm conclusions. There are numerous open questions still, including the eligibility rules and the system that would be used to count the votes. For the latter, Debian's devotee and the Condorcet Internet Voting Service (which is used for elections to the Linux Foundation Technical Advisory Board) have been proposed. The Git project is considering the addition of a fundamental piece of governance policy, which is not something to be done lightly, so a conclusion may be some time in coming. The voting process is meant to help in situations where a consensus seems unlikely to emerge, but that process itself almost needs a consensus behind it before it can be adopted.

Locking down hibernation for the winter

2026-11-12 00:00:00

by: Daroc Alden

By Daroc Alden

November 6, 2026

When a computer hibernates, the kernel writes the contents of memory to disk and then shuts the system down. Resuming from hibernation involves reading that data back into memory, and then having the kernel pick up where it left off. Unfortunately, the kernel does not have any way to know that the data it is reading back has not been tampered with, which is why lockdown, an optional kernel feature that attempts to prevent modifications to the running kernel, disables hibernation. Matthew Garrett, who has been working on lockdown for many years, has shared a patch set that aims to fix this problem. His solution must also protect against downgrade attacks (where an attacker reboots the computer with an older kernel version to bypass new protections), which complicates the implementation.

The basic idea of Garrett's patch set is not complicated: sign the saved hibernation data with a cryptographic key that only the kernel has access to. The problem turns out to be figuring out how to obtain such a key. A static, known key is useless for this purpose, since it could be used to forge the signature. A key stored in the computer's trusted platform module (TPM) is a better choice. The kernel sits between the TPM and user space, and so it can forbid user space to read the chosen key, keeping it secure. Additionally, the TPM can be configured to withhold the key when booted from a different kernel, although this is not as straightforward as it may seem, because older kernels will still, for example, possess correct secure-boot signatures.

The primary motivation behind involving the TPM is to avoid downgrade attacks. Given that older kernels won't know to forbid TPM access, an attacker could, theoretically:

  1. From a newer kernel with lockdown enabled, trigger hibernation.
  2. Boot an older kernel, with resume and swap disabled.
  3. Ask the older kernel for access to the chosen TPM key.
  4. Tamper with the saved hibernation data and re-sign it.
  5. Reboot into the newer kernel, allowing the system to resume from the tampered data.

One of the core features of a TPM is the ability to lock down secrets such that they can only be read when the hardware is in a known state. The TPM relies on platform-configuration registers (PCRs) to keep track of hardware state. These registers cannot be written directly. Instead, the TPM resets them to zero when the system boots, and then software running on the system can provide values that are hashed with the current state of the PCR to produce a new value.

So, for example, when the computer's firmware starts executing, it can check a signature on the bootloader, and add a marker to a specific PCR to indicate that it validated the signature against a particular secure-boot key. Then the bootloader can do the same thing to check the state of the operating system and the attached hardware, and so on. In theory, this ensures that the PCR can only reach a particular state when the operating system and hardware have not been tampered with.

In practice, the implementation is more complicated. There are multiple PCRs that are used for different purposes. For example, systemd uses PCR 11 to indicate which boot phase the system is in. This can be used to ensure that a key stored in the TPM (a disk-encryption key, for example) is only accessible while the initial ramdisk (initrd) is running. When the system is about to transition to the normal root filesystem, systemd writes "leave-initrd" to the PCR, changing its hash in a way that cannot be undone until the system is rebooted. The process of writing an additional piece of information to a PCR to invalidate a key associated with it is called "capping" the PCR.

If the kernel had a PCR that it capped prior to starting user space, it could extend that PCR with a new value, bind a key to the resulting PCR state, and thereby ensure that the key was only readable by new versions of the kernel and not by old versions. The kernel does not currently cap any PCRs, however, leaving that up to user space. So, a malicious user-space application running on an old kernel could still extend a PCR with the value that the new kernel expects, thereby putting the TPM into the "new kernel" state even on an old kernel.

The solution is "something horrifying" that Garrett came up with. PCR 5 is used by the UEFI firmware to perform hardware measurements, and is capped when ExitBootServices() is called, to prevent later components from faking hardware information. The kernel starts executing its boot stub before UEFI exits, since it may need to communicate with the firmware to bring the system up. Therefore, Garrett has added code to the boot stub to insert a marker into PCR 5 indicating that the kernel supports blocking user-space access to a TPM key before the firmware caps it. Since user space is not started until after that point, it has no way to fake the marker, even on an older kernel.

On its own, however, this is not enough. The state of PCR 5 only demonstrates that the computer booted with a new-enough kernel; it doesn't prevent user-space from creating its own key that is bound to that state of PCR 5, and then signing the hibernation data with that key. When the new kernel boots after hibernation, it would see a signature by a key bound to PCR 5, but it would still not be able to prove that key was created inside the kernel (and therefore hidden from user space).

So, Garrett's patch set goes further. Interactions with the TPM can be divided into individual sessions. His code allows those sessions to be audited, generating a signed digest. Those digests are signed by the TPM itself, which means that having a signed digest proves that, at some point, those commands really were sent to that particular TPM, and produced those particular results.

Combined with the use of PCR 5, the entire procedure to produce a signed hibernation image becomes:

  1. The new kernel boots, writing a marker to PCR 5.
  2. The firmware caps PCR 5, preventing user space from mimicking the kernel's marker.
  3. The kernel starts a new session with the TPM, where it checks that PCR 5 is in that state and then generates a new signing key.
  4. The transcript of the session is hashed, signed by the TPM, and stored alongside the hibernation data.
  5. The hibernation data is signed with the newly created key.

Then, on reboot, the kernel goes through a number of verification steps before loading the hibernation image:

  1. The kernel checks that the signed transcript digest was signed by the current TPM.
  2. It checks that replaying the transcript produces the same digest.
  3. It checks that the transcript holds the correct commands to the TPM, and only those.
  4. It checks that the transcript read PCR 5, and that the value matches the current value of PCR 5.
  5. Finally, it checks that the key produced by the transcript is a valid signing key that was used to sign the hibernation data.

The end result of all of this work is that users running lockdown kernels should be able to enable hibernation, and trust that the kernel cannot be tampered with between the computer shutting down and resuming from hibernation. Attackers cannot change the data directly, because it is signed; cannot access the key used to do the signing, because the kernel prevents it; cannot work around that restriction with an old kernel, because the TPM binds the key to a state that only new kernels can produce; and cannot create their own key that would be accepted, because they cannot forge the key-creation transcript.

Garrett's patch set has received a small amount of comment. James Bottomley asked about using a hardware feature called "localities" (an access-control mechanism that restricts operations to specific CPU privilege levels) to implement something like this more simply. Garrett agreed that localities "are very clearly the Right Way to deal with this," but did not think that the kernel could make use of them, because hardware support is typically limited to specialty devices. Most consumer devices have a TPM, but not one that supports the necessary extensions.

Bottomley also pointed out that having the firmware cap PCR 5 is not universal; his XPS-13 9380 Core i7 (released in 2019) does not cap that register. Garrett was disappointed to hear that, but still thought the patch set was worthwhile, given that newer computers do tend to cap PCR 5. Also, the implementation could potentially be swapped out for other hardware-specific solutions, if needed.

The patch set will need a second version to respond to the reviews. Garrett has been working on enabling hibernation under lockdown since 2021, but this time it seems that he's settled on a design that systematically prevents downgrade attacks. It may not be too much longer until his goal is finally realized.

User namespaces + file capabilities = trouble

2026-11-12 00:00:00

by: Jonathan Corbet

By Jonathan Corbet

November 5, 2026
User namespaces are a key part of the kernel's toolkit for assembling containers; processes within a user namespace can appear to have full root access to the system while gaining no extra privileges in the wider system. At least, that is the intent. In practice, keeping privilege contained within a user namespace has often turned out to be difficult. As an example, consider this small patch series from Josef Bacik, which is intended to address some situations where a process within a user namespace can elevate the privileges of processes outside of it.

Some background

The first process that is placed into a user namespace is treated much like the init process in the base system; it runs with user ID zero and has full root privileges. The kernel, though, remaps all user IDs before using them for any access decisions outside of the container. By default, all user IDs are mapped to the "unknown user" ID 65534 before, say, accessing a filesystem mounted outside of the namespace. So root access within the namespace may translate to no access at all outside. If namespaces have been nested, there may be multiple levels of remapping applied before reaching the initial namespace created when the system boots.

It is possible to change the user (and group) ID mappings for a user namespace by writing to the uid_map or gid_map file in the /proc directory of any process running inside that namespace. Without root privilege, though, it is not possible to remap IDs to anything other than that of the process that created the namespace. If an unprivileged process with user ID 1000 creates a user namespace, it can set up a mapping from any ID within the namespace, but only to ID 1000 outside. Changing the mappings is also a one-time operation; once the mappings have been set, they cannot be changed again.

One other bit of important background is capabilities, which describe the privileges that any given process has. The root user, by default, has all capabilities; other processes have none. There are times, as we will see, where a process running as root will drop some of its capabilities to prevent certain actions from taking place.

Finally, file capabilities can be thought of as a way to create a form of setuid executable. A given set of capabilities can be attached to a file with the setcap command; thereafter, any process running the program in that file will be given the named capabilities. Needless to say, attaching capabilities to a file in this way is a privileged operation; specifically, any process attempting to do so must have the CAP_SETFCAP capability. The kernel has some elaborate mechanisms to allow file capabilities to work within a user namespace while being ignored outside. Specifically, "version 3 extended attributes" can encode a non-root user ID that can map to root inside a namespace owned by that ID. The curious can see this subsection of the capabilities man page for the gory details.

The trouble with file capabilities

User namespaces were designed to map the root user internally to an unprivileged user externally. But it is possible to map root within a namespace to root in the containing namespace as well. Doing so clearly presents a number of security challenges but, with sufficient care, a root-mapped user namespace can still provide a fair amount of containment. This is especially true if the code that runs as the init process within the namespace is trusted by whoever manages the containing namespace. That code can do whatever setup is needed, then drop privileges (capabilities) before transferring control to whatever workload the container was meant to run.

If the root user within a user namespace adds file capabilities to an executable file that is visible in the containing namespace, those capabilities will normally be qualified by the user ID that root maps to in the containing namespace. As a result, those capabilities will not be effective if an unprivileged user runs the executable in the containing namespace. If, however, the contained namespace is root-mapped, this qualification does not happen and the capabilities are effective in the containing namespace. Letting root add capabilities to a file in this way could, thus, allow privilege to escape the namespace.

The way to prevent this from happening is to take care to drop CAP_SETFCAP from the root process running within the namespace; that process can no longer create file capabilities, and the privilege escape goes away. At least, that happens until this root process creates a root-mapped user namespace of its own. Remember that the initial process running in a new user namespace has all capabilities, so that process will have regained CAP_SETFCAP. It can then add file capabilities to a file in the containing namespace which, being root-mapped as well, will propagate the change through to its containing namespace. At that point, there is, once again, a file with elevated capabilities, accessible outside the namespace, that an unprivileged user could execute.

This commit, merged just before the 5.12 kernel release in 2021, is meant to address that problem. If a process tries to create a root-to-root mapping by writing to a namespace's uid_map file, the attempt will fail unless that process possesses CAP_SETFCAP. That alone does not suffice, though, since the root process within a newly created user namespace does hold that capability, and could write to its own uid_map file (an operation that is allowed if the effective UID within and outside of the namespace are the same). So that patch also records whether the creator of the namespace in question had CAP_SETFCAP; in the absence of that capability, an attempt to create a root-to-root mapping from within the namespace will fail. Problem solved.

More leaks

Naturally, the problem is not truly solved, or this patch set (you remember the patch set...this is an article about Bacik's patch set) would not exist. It turns out that requiring CAP_SETFCAP to create a root-mapped user namespace is not enough to prevent privilege leaks in some situations.

Imagine a root-mapped user namespace with two root processes; one of them (call it "A") holds the full set of capabilities, while the other ("B") does not have CAP_SETFCAP. If A creates a user namespace of its own, that namespace will have the "creator held CAP_SETFCAP" flag set. B can then enter that namespace with a setns() call; since its UID matches that of the creator of the namespace, that entry will be allowed, and B will have the full set of capabilities in that namespace. At that point, B can write a root mapping into the uid_map file, then start attaching file capabilities that will be visible outside of the containing namespace. In other words, B will have regained the CAP_SETFCAP capability that had been dropped.

There are other scenarios as well. If A were to open the uid_map file without writing to it, then somehow transfer the file descriptor to B, it would be possible for B to write a root-to-root mapping there. The check for CAP_SETFCAP is done when the uid_map file is opened, not when it is written, so that mapping will be allowed. One might argue that A should not be giving away a privileged file descriptor that way, but it could happen if A simply fails to close it before dropping CAP_SETFCAP.

If B creates a user namespace, the CAP_SETFCAP flag will not be set, so B will not be able to create a root mapping for that namespace. A, however, has that capability, so it can write a root mapping into B's new user namespace. Once again, that will enable B to set file capabilities that are effective in the containing namespace. In some cases, there can be multiple levels of mappings that involve non-root UIDs in the middle. ID-mapped mounts, which are often used with containers, add a twist of their own, since a non-root UID on the underlying filesystem may appear to be root within a give mount namespace.

Finally, B could simply attach to A with ptrace(), an operation that is allowed because the effective UIDs are the same, then cause A to write its uid_map file or set file capabilities directly. Since A holds CAP_SETFCAP, those operations will be allowed.

Plugging the holes

Preventing these privilege leaks requires enhancing the tracking of CAP_SETFCAP and some changes that are visible to user space. The first patch in the series replaces the parent_could_setfcap boolean in the user_namespace structure with an integer setfcap_level field. While the old boolean recorded whether the creator of the user namespace had CAP_SETFCAP, the new one records how far up that capability was present — how many levels of parent user namespace where it was also held. This new variable accounts for the fact that CAP_SETFCAP in the current user namespace is effective in that many parent namespaces as well.

This patch is intended to prevent a process from gaining CAP_SETFCAP on an ancestor user namespace by using setns(). Specifically, it adds a check to ensure that, when a process calls setns() to enter a user namespace that is root-mapped at some higher level, the setfcap_level of that process extends at least as far as that of the target user namespace. The test for root-mapped user namespaces includes namespaces that have not yet had a mapping set at all, since they still could become root-mapped in the future. If the setns()-calling process does not have CAP_SETFCAP with sufficient reach, the call will fail with an EPERM error. This is one of the visible changes; that call would succeed in current kernels.

A similar change is made by this patch to control setting a root mapping by writing to the uid_map file. If the attempted write creates a mapping to the root user in any ancestor user namespace, then the writer's setfcap_level must extend at least that far, or the operation will fail. This patch addresses the case where a CAP_SETFCAP-holding process writes the uid_map file; it checks attempts to write file capabilities and ensures that the writing process has a setfcap_level that is high enough to reach any root-mapped ancestor. Finally, this patch applies a similar check to ptrace() calls; if the tracer does not have a setfcap_level that reaches at least as far as that of the target, the call will fail.

This series has been through eight revisions as of this writing; it has evolved considerably, though the last few versions have been mostly focused on adding tests. In theory, with these patches applied, the ability to leak privilege out of user namespace with file capabilities should no longer exist. In practice, there is enough complexity here that one might still have cause to wonder. Ensuring that user namespaces are truly secure has been a multi-year endeavor; mapping root access outside of these namespaces is only going to make that task more challenging.

Additional hardening for the glibc dynamic linker

by: Daroc Alden

By Daroc Alden

The Node.js project recently had a security vulnerability that affected its Brotli decoder. The bug was a buffer overflow, but the particular way that official Node.js binaries are built for Linux meant that one of the main protections against turning a buffer overflow into remote code execution, address space layout randomization (ASLR) could not be turned on. If ASLR had been enabled, the bug would still be exploitable in theory, but much more difficult to exploit in practice. In response, the GNU C Library (glibc) is considering a new set of tunable settings to allow administrators to forbid programs that do not support ASLR. The new settings, while a welcome hardening measure, may not address the root problem.

Background

When a program contains a buffer overflow, it is frequently possible to use that buffer overflow to take control of the program's execution, turning a data-corruption bug into a remote-code-execution vulnerability. Generally, this is done by overwriting a pointer that the program later jumps to, redirecting the program's flow of control to an attacker-chosen address. From there, it is straightforward to, for example, call execv() with attacker-controlled arguments. The pointer that is overwritten is often a return address on the stack, but similar attacks have been demonstrated with callbacks, indirect jumps within a function, and C++ virtual method tables.

There are many mitigations intended to make this more difficult for attackers, including control-flow integrity, shadow stacks, and even tweaking code generation to reduce the number of useful places to jump to. ASLR is arguably the simplest such mitigation. It uses the fact that modern compilers can emit relocatable code to place the program in a randomly chosen part of virtual memory. Attackers wishing to overwrite a function pointer must figure out the program's base address in order to divert control flow anywhere useful.

Compiling to position-independent code does have an impact: such code is often slightly larger and slightly slower than position-dependent code. In 2020, Node.js contributor "woodfairy" measured the impact on Node.js in particular at a slowdown of 5-10%, depending on workload. That slowdown was judged acceptable on macOS, but not on Linux (except for Android, which forbids position-dependent code, forcing the choice).

Several Linux distributions, including Debian, Ubuntu, Arch, Alpine, and Gentoo, enable position-independent executables by default. On those distributions, compiling Node.js from source or installing the distribution packages will enable ASLR. The official Node.js binary packages, which are compiled on a system running Red Hat Enterprise Linux 8, still do not.

Dynamic linking

Dynamically linked programs rely on the dynamic linker to initialize a new process. On Linux, the linker is typically provided by the glibc project, although there are distributions that make other arrangements. That linker supports configuration options known as tunables to affect its operation. These can be set by environment variables, or system-wide in a file at /etc/tunables.conf.

On October 26, Daniel Colascione asked the glibc development mailing list whether it made sense to add a new tunable that would forbid position-dependent executables. Adhemerval Zanella Netto responded with a list of hardening-related tunables that he hoped to implement, saying that they were all on his to-do list. He also suggested adding a single glibc.hardened tunable to enable all of them as a batch, similar to GCC's -fhardened option.

Zack Weinberg noted that, because most fixed-position executables are linked at low addresses, users can ask the kernel to refuse them by setting the minimum mmap() address (the vm.mmap_min_addr sysctl) to a higher number. He did note there were some problems with the idea, and Maciej Rozycki pointed out more.

Zanella posted the implementation of his promised tunables on October 28. The project's default behavior remains the same, but each option can be set to 0 or 1 (depending on its wording) to enable the new protections. The new options include:

  • glibc.rtld.require_pie=1, which requires loaded programs to be position-independent.
  • glibc.rtld.textrel=0, which forbids programs that ask the linker to perform a relocation targeting a section of the executable that is not mapped as writable.
  • glibc.rtld.wx_segments=0, which forbids programs that ask for some segments to be mapped as both writable and executable at startup.
  • glibc.rtld.bind_now=1, which disables the use of lazy global offset table resolution (equivalent to the use of the LD_BIND_NOW environment variable).
  • glibc.rtld.relative_rpath=0, which prevents dynamic libraries from being found via relative paths.
  • glibc.rtld.relro={1,2}, which requires the use of relocation read-only (RELRO) or -z now, respectively.

All six of the options can be set to the hardened behavior at once with glibc.rtld.hardened=1. Yury Khrustalev found many of the names overly terse, and suggested that longer names, such as allow_textrel, might be clearer. Zanella agreed to elongate them in the next version of the patch set.

The changes themselves drew little comment. Most of them should be possible for distributions to enable with minimal disruption. In particular, the distributions that already enable position-independent executables by default can enable the tunables without impacting any distribution packages. The more difficult problem will come from executables built outside the distribution. Unless widespread adoption of these tunables motivates projects like Node.js to abandon position-dependent code, users may need to disable the tunables for those programs that the tunables are intended to address.

Containers as a recognized kernel object

2026-11-05 00:00:00

by: Jonathan Corbet

By Jonathan Corbet

October 29, 2026
The foundation of the design for containers in the kernel is that there isn't one; there is no container abstraction that the kernel recognizes. Instead, the kernel provides a long list of components — namespaces, control groups, sandboxing mechanisms, and more — along with a note that says, in effect, "some assembly required". There have been attempts (repeatedly) over the years to turn containers into first-class objects with kernel support, but they have never gotten far. Now Josef Bacik is making a try with a concept that he calls "cells".

Some years ago, the lack of any sort of kernel-supported container object was arguably the right approach; there was still a lot to be learned about how this concept should be integrated into Linux. Some would surely argue that it is still a good idea. But there are downsides as well, starting with the complexity of creating a container. Beyond that, though, since the kernel has no notion of containers, it cannot enforce a container's properties and cannot even answer questions about which container a process might belong to. Containers are created by walling off parts of the larger system. Namespaces are created then entered, filesystems are unmounted or overmounted to make them inaccessible inside the container, and so on. This sequence means that any given process might be only partly inside a container, a situation that, according to Bacik, "is where a depressing number of our bugs come from". The current approach to container creation also makes it easy to let unwanted resources leak into the container from the outside.

Introducing cells

Bacik's proposal is an attempt to address these problems. A container (called a "cell" in this series), when created, contains nothing at all. No processes or filesystems show up there by default. Anything that the creator wants to exist in a cell must be explicitly put there. Processes and other resources created within a cell are not allowed to to leave that cell. In theory, cells should be easier to manage and easier to keep secure than containers as they exist in Linux now.

A cell's life starts with a call to cell_create(): 

    int cell_create(int parent, unsigned int flags);

The parent parameter is seemingly meant to designate which process will be the parent of the new cell, but in the current implementation the only allowed value is CELL_SELF, meaning that the creator is the parent. The flags argument must be zero. The return value, if all goes well, is a "cellfd" — a file descriptor referring to this cell. The cellfd is special, in that it is the handle that is used to perform all other operations on the cell. There is no way to create a duplicate cellfd that possesses the same capabilities. Creating a cell is an unprivileged operation.

If the cellfd is closed, the cell (and anything contained within it) is immediately killed. There is also a system call to kill a cell explicitly: 

    int cell_kill(int cellfd, unsigned int flags);

Where cellfd identifies the cell to kill, and flags must be zero.

An empty cell is secure and bug-free, but it is also rather boring. There is another system call that is used to set various properties of this cell to make it more interesting: 

    int cell_configure(int cellfd, unsigned int cmd, const char *key,
    		       const void *value, int aux);

This system call applies the given configuration cmd to the cell identified by cellfd; the key string identifies which property is to be changed. The available commands are:

CELL_SET_FLAG
Sets the flag named by key; there are no flags defined in the current proposal, though.
CELL_SET_STRING
Sets the string value given by key to the given value. Two strings are supported in the initial patch set: hostname to set the host name within the cell, and net, which sets the network namespace for the cell. By default, the cell has no network access, and only AF_UNIX sockets can be created within it. Setting the net key to new creates a new network namespace that the builder will subsequently configure, while own creates a network namespace owned by the cell itself and configured internally. In the new case, there is another new system call (cell_open()) that must be used to obtain a file descriptor for the newly created namespace. The network namespace can also be explicitly set with CELL_SET_FD, described below.
CELL_SET_BINARY
Sets the property identified by key to the provided binary data. The only value accepted is ids, which is used to define which user IDs will be used within the cell. There are only two allowed values. Setting it to one causes processes within the cell to run with the same user ID as the creator; this mode is not allowed for the root user.

Otherwise, the ids key must be set to 65,536, which causes a block of that many IDs to be allocated from the upper part of the 32-bit user-ID space. These IDs will be unique on the running system, and the cell creator has no control over what they will be. It is not possible to create files owned by those IDs in any filesystem outside of the cell. This part of the design has drawn some comments and may change (perhaps by providing an entirely separate user-ID space for cell inmates) in the future.

CELL_SET_FD
Sets a value requiring a file descriptor. There are three of those implemented in this patch set. root is a filesystem namespace that contains the root filesystem within the cell, net is a network namespace to be used by the cell, and budget is a control-group directory. The budget is mandatory, and each cell must have its own control group.
CELL_CMD_SEAL
Once the configuration of the cell is complete, this command must be issued; it completes the initialization of the cell and prevents any further configuration changes.

Once the cell is sealed, it is set up with a filesystem tree, control-group membership, and the rest of the namespaces that control its interactions with the rest of the system. It is still otherwise empty, though, with no processes running within it. In Bacik's design, there is no way for an existing process to enter a cell; setns() cannot be used to enter its namespaces. Instead, processes must be born within the cell from the beginning, and they can never exit the cell.

Creating inmate processes

Allowing the creation of processes with life sentences inside a cell involves yet another proposal for a process-builder API; the last such attempt was covered here in August. Here, the first step is to create the process within the cell with a variant of the pidfd_open() system call. Rather than passing a process ID to pidfd_open(), the cell creator passes the cellfd and the PIDFD_EMPTY flag. The return value is a pidfd that does not, yet, refer to a running task; it is in the "embryo" state at this point.

Once the pidfd is created, it must be configured with another new system call before it can run anything useful: 

    int pidfd_configure(int pidfd, unsigned int cmd, const char *key,
    		        const void *value, int aux);

The interface looks much like that of cell_configure(), and it operates in mostly the same way. The process to configure (which must be in the embryo state) is specified by pidfd; the cmd value is one of:

PIDFD_SET_STRING
The only supported key is exec, which names the executable file (within the cell's mount namespace) that the process will run.
PIDFD_SET_BINARY
Sets a key to binary data. Recognized keys are argv to set the processes argument vector, envp to set its environment variables, and cred, which sets the process's user and group IDs within the cell's user namespace.
PIDFD_SET_FD
Sets a file descriptor in the embryo process; the key is the file-descriptor number (as a string), and the aux parameter is an open file descriptor in the caller's file table. The only open file descriptors the process will have are those set up with PIDFD_SET_FD, so there should be no problems with file descriptors accidentally leaking into the cell.
PIDFD_CMD_START
This command sets the process running once all of the necessary parameters have been configured. After that, it is no longer an embryo, and pidfd_configure() can no longer be used with it.

The first process to be started within the cell becomes the init process for the cell; if it dies, the cell dies with it. It is possible to inject other processes into a running cell using this API, so the owner can, for example, start a shell within the cell if need be. But that must be done by creating a new process; existing processes are forbidden from crossing that boundary.

Other details

A lot of other restrictions at the cell boundary exist as well. Every process within the cell runs with the "no new privileges" flag set, so it cannot gain new capabilities. It is not possible to send open file descriptors across the boundary (in either direction) using Unix-domain sockets. Cells cannot share a control group with any other processes. And so on; the purpose is to make the containment of cells as tight and controlled as it can be.

There are a lot of details to this proposal that have not been covered here; it also contains a long list of open issues and shortcomings. As Bacik noted, the purpose is not to provide a complete implementation; instead, it "exists so that there is code to argue about". Readers wanting to know more should read through his entire proposal. The code exists in a GitHub branch; it contains a design document that covers much of what was discussed here and more as well.

So far, there has been little discussion of this proposal, perhaps because it was only posted to the linux-fsdevel mailing list. Nonetheless, it has evolved somewhat since the first version was posted in mid-October. This is not a small proposal, and it is trying to make changes that have proved controversial in the past, so it is not hard to imagine that discussion will eventually happen. At the far end of it, though, the kernel might just have the container abstraction that its community has resisted for so long.

In addition, they wanted to hear from attendees about their needs in this area.

Background

O'Donell began by describing "the problem we're trying to solve", which is to make kernel functionality that is exposed by system calls easy to use from the C library. If a system call is available, the feature has already been added to the kernel and there is an entry in a header file to access it. There are lots of reasons developers want access to new system calls, for testing, examples, sorting out ABI issues, and so on, he said.

Currently, there are libraries "that encapsulate entire sets of syscalls", such as liburing and liburcu (which were listed in the slides, but not explicitly mentioned at the time); the developers of those libraries "have done a very good job of exposing that functionality", but often not directly as system calls. The specialized-library developers may choose to offer a different interface that may be easier for programmers to use.

What O'Donell wanted to talk about was all of the other system calls that are lacking any glibc interface (other than syscall()). There is a bunch of complexity in creating system-call wrappers, "because of ABI issues, procedure-call standards, the way in which parameters are passed to the kernel, the special kernel parameter-calling interfaces that you have", and so on. Due to that, it is difficult to write portable versions of system-call wrappers, which means they end up as "weird, per-architecture-specific things". Creating those wrappers should not require understanding all of that, he said.

So, at last year's session, he offered to "review, coach, [and] mentor syscall wrappers through the process". When kernel developers add a system call, there are multiple communities they need to work with in order to actually provide the feature to users, such as musl libc, LLVM-libc, and others. His offer was to try to make that process easier for getting system-call wrappers into glibc.

"Ta-da", he said, with a slide showing an RFC patch set from André Almeida to add a wrapper for futex_waitv(). O'Donell thanked Almeida, who was present, for taking him up on his offer, noting that the two of them have been working on a patch set with Adhemerval Zanella. The futex interface is complicated, O'Donell said; it is a "multiplexed interface with really gnarly, fiddly pieces", but the wrappers are a work in progress. "I think this is the start of a beautiful series of patches, of collaborating with us to make sure that we get the wrappers in place."

Missing

Next, he turned to the specific system calls without wrappers. He looked at the x86-64 architecture, which has 386 system calls in the Linux kernel tree. Of those, glibc is exporting 292 "same-named globals", which means that there is a C function in glbc with the same name as the system call. That call "basically does that functionality; I'm not saying that it's exact or identical". For example, some wrappers need to map kernel types into the equivalent user-space-ABI types.

There is a mixture of mechanically created assembly language wrappers and manually created C wrappers, which is less than ideal, perhaps, but is where things stand, he said. Since 2014, the glibc developers have been looking at ways of mechanically generating wrappers, "but the mechanical-conversion process is so fiddly" because there are so many different details that need to be taken into account. So that project has never been completed.

Beyond the 292, there are 16 glibc calls that have different names than the system calls because the behavior is different. That leaves 77 system calls with no wrapper. Toolchains track organizer Nick Desaulniers asked if there were any of those 77 that are "dead and should be slated for removal". O'Donell enthusiastically agreed that there were: "absolutely"; he noted that Desaulniers had anticipated his next slide (seen below), which contained the answer. The slide had an opinionated list of the priorities for adding wrappers that was compiled by O'Donell, Weimer, and Zanella.

O'Donell said that he didn't expect attendees to really read the slide, but to just get a general idea of the different buckets that had been used to classify the system calls. The first bucket was "core-kernel functionality", which Weimer and O'Donell went back and forth over, moving calls from there to the "domain-specific functionality" bucket and back again. "For the 'domain-specific functionality', I don't think we want wrappers for them", O'Donell said. At the top of that list is calls for io_uring, which are not a priority for wrappers because developers will simply use liburing. If that turns out not to be true, thus kernel and user-space developers are asking for wrappers, the glibc developers may add them at some point, but there are higher priority targets.

Another lower priority area is system calls that implement interfaces needed by C-library implementations. Those can be called directly from the C-library code and are not functionality that many application developers will need, he said. Then there are "the things that are dead" listed at the bottom of the slide "that we'd never implement".

Concurrency

Going back to the top-priority system calls, he noted that there are a number of concurrency primitives, such as futex_waitv(), that the kernel exposes which need wrappers. That is what is behind Almeida's efforts and those wrappers are needed elsewhere, such as in libstdc++, O'Donell said. Since they were not available, "we hack it up and libstdc++ calls futex() directly", which should not have happened.

Beyond the concurrency primitives, there are various calls for scheduling, isolation, memory management, filesystems, and so on. At the bottom of core-kernel functionality section is map_shadow_stack(), which may not quite have the same priority, O'Donell said. But once futex_waitv() gets in, it makes sense to start working on more of the concurrency calls as part of the core-kernel functionality category.

O'Donell noted that Weimer wants to add wrappers for membarrier() and rseq_slice_yield(), but asked about get_robust_list() and set_robust_list() (which came up in Almeida's session at LPC 2025). Weimer said that those calls should not have glibc wrappers; "that needs to be more efficient, because you can't do a syscall when you need it".

O'Donell asked Almeida if he would sort the list of concurrency primitives differently, but Almeida said that it looked good to him. He wants to get futex_waitv() wrapped because it is used for emulation, but "eventually I would like to have some sort of pthread_wait_on_multiple() as well and I think this is the first step". That would be like the Windows WaitForMultipleObjects() function, O'Donell suggested, which is a powerful primitive that is lacking in Linux. Almeida agreed and said that the hard part has already been done in the kernel; O'Donell and he agreed that a collaboration between glibc and kernel developers to determine how that interface would work is a good next step.

There are legacy system calls that the kernel has to support forever, Steven Rostedt said, in order to keep running code that was written in the 1990s. But that does not mean that they need to be available for code bases that are newer and do not require those calls, which may have a security benefit since the legacy calls are less scrutinized. So he suggested that a list of these system calls be collected and then a kernel-configuration option could be added to remove them from some kernel builds.

O'Donell said that the glibc maintainers have discussed ways to harden the library, including removing system calls from it. "If you never call exec(), why are you allowing exec() to exist as a callable global symbol?" Weimer noted that some people have started removing the 32-bit time system calls from glibc, in favor of the 64-bit calls, but that is problematic for the glibc developers because the 32-bit versions are used internally. Glibc still needs to run on kernels that only have 32-bit time values. "If you disable the support for reasons, then stuff breaks because we are actually using them for compatibility with older kernels."

Conflicting symbols

Earlier, Almeida had asked about symbol conflicts, which O'Donell acknowledged as a difficult problem. He does not think there is a silver bullet for handling symbol conflicts between different libraries and header files; it is "possibly an ecosystem problem where we have to work [it] out with individual projects". He likened it to the effort he and Weimer were involved in to move all of the Fedora packages to C99, which was a "cross-cutting ecosystem project" that required lots of volunteers fixing each problem as it arose.

Weimer said that the conflicts most often occur when someone wants to use "the official libc functionality" so they include the appropriate glibc header file but also need something from kernel header files in the same compilation unit. That may cause conflicts. Fixing those problems requires more coordination between the glibc and kernel projects.

Weimer said that his highest priority is to complete the wrappers for existing functionality, restartable sequences in particular. Another high priority is on "system calls that have a strong C library dependency" because there is a global object that needs to be accessed in a coordinated way. His example was for system calls that affect the thread control block (TCB), which should not be manipulated from two separate user-space libraries. Right now, the C library uses the TCB for locking, while web browsers use the clone() system call wrapper from glibc, but "then do a longjmp() out of that and then patch the TCB so that the rest of the C library works and that is horrible for backwards compatibility". The browsers need to know the structure offsets in the TCB in order to do that; his hope is that working on system calls with a TCB dependency will allow moving the browsers to "a model that's supportable longer term".

Another area he would like to see dealt with is system calls that have non-portable signatures; futex() is a good example because there is also the incompatible futex_time64(). On some architectures you have to use futex() and others futex_time64() but having an #ifdef on every call site is not really going to happen. Arnd Bergmann said that the older, 32-bit-only calls will be going away anyway, because the kernel cannot support 32-bit times. Weimer seemed to be hoping that futex() was not slated for removal from the kernel, but Bergmann was adamant that it was. Weimer suggested making timestamps unsigned, which would extend the life of 32-bit times (at the expense of being able to represent times before 1970), but there was no response to that.

Enumeration

H. Peter Anvin said that the kernel needed to provide a mechanism for enumerating system calls, which would allow using the GNU indirect function (IFUNC) feature. Right now, a program does not know that a system call is not implemented until it gets an ENOSYS error, and "the opportunity to use IFUNC has already long since passed". Weimer did not think that would help much because seccomp() filters can also return ENOSYS; it would be nice if the kernel provided a complete view of what is permitted that included seccomp() restrictions.

It might make sense to have the kernel provide its own library for the simple and straightforward system calls, Anvin said. That would decouple the release schedules for distributions; some conservative distributions want to update glibc less frequently than the kernel, he said. O'Donell suggested looking at the BSD design, where the kernel provides a system-call dynamic shared object (DSO), which is used as a filter for the C library DSO. If a call is not present in the kernel DSO, the one from the C library is used. If the kernel starts implementing new system calls, "they just pop into existence". He thought it might be worth reviewing that mechanism to see if Linux could benefit from that approach.

Kees Cook returned to the seccomp() filters and wondered what kind of information was needed. That code maintains an internal bitmap of system calls with three states indicating whether seccomp() will always allow it, always reject it, or "I have no idea, there's a filter attached to it". That information could be exposed to the C library somehow, he said. Weimer thought that might be useful, but "that is more like the finishing touches, we have much more work to do before we get there", he said to laughter.

For example, Weimer said that map_shadow_stack() suffered from seccomp() filter problems too. Glibc can use prctl() to enable shadow stacks, which succeeds. Later it may try to create a new shadow stack, but map_shadow_stack() fails due to a seccomp() filter. He would like to make that work.

Another problematic system call is membarrier(), he said. He had a patch set to add it to glibc, but while that was in progress, the kernel developers added a new parameter to the system call. "That is a bit of a turn off for writing a wrapper when you don't know what the signature is." Fixing the signature in stone while arguments are still being added is problematic on the glibc side.

Once his high-priority items are addressed, Weimer said, he wants to "basically get out of the wrapping business" by improving the generic system-call wrappers. There would be three variants, the existing _syscall(), one for system calls that return twice like vfork() (named _syscallr()), and one that allows canceling system calls (_sycallc()). The return-twice variant needs an attribute so that GCC and Clang do not apply invalid optimizations. Cancellable system calls are not possible with the existing wrapper, but the new wrapper would arrange that the system call can be interrupted in a safe way, that the cancellation handlers are run, and that the thread exits. In addition, the new wrappers would switch away from using long for register types, which is not the right type for some architectures.

The wrappers would allow easier testing for new system calls, though they would not provide the type safety that the eventual full system-call wrappers will provide. O'Donell said that it will allow developers to immediately start using new system calls. Anvin was concerned that new testing features "have a nasty nasty tendency to end up in production". Weimer said that it is "not worse than ioctl()", which was met with laughter. He is concerned that putting more friction into the paths of developers, in the form of requiring automatically generated system calls in the virtual DSO (vDSO) or similar, will just cause them to turn to ioctl()-style interfaces.

Anvin thought that if the system-call wrapper was generated out of the kernel build, it would alleviate much of the problem. O'Donell agreed, but thought that was a longer-term solution; until then, the new wrappers would effectively be "a honeypot to catch people wanting to write syscall pieces". That can lead to a conversation about getting a proper wrapper added to glibc. In parallel, the discussion about other ways to improve the situation should be pursued, he thought.

O'Donell and Weimer were out of time at that point, so they wrapped up quickly with a question for attendees to consider: what other system calls could be added to glibc to make their lives easier? They suggested using the kernel-features repository that is part of the UAPI group at GitHub as a place to gather ideas.

Removing binder.c

2026-11-05 00:00:00

by: Daroc Alden

By Daroc Alden

October 30, 2026
Kangrejos

The final talk at Kangrejos 2026 was about the removal of the C implementation of Android's Binder driver, the primary interprocess communication mechanism used on Android devices. Carlos Llamas announced that he had deleted the C code to general applause, and then shared some insights about what went into replacing the C implementation. Alice Ryhl, who has worked on the Rust implementation for some years, added her own thoughts about what the most difficult and interesting parts of the transition were.

Binder was added to the kernel in 2008, Llamas said, as an interprocess communication mechanism for Android devices. Its design originated in BeOS, but it has grown significantly since then. It provides a rich set of operations for allowing processes to communicate with the minimum amount of overhead. It also, therefore, presents a large attack surface for Android. Many complicated chained attacks against Android have involved Binder at one step or another, Llamas explained. Google's internal "red team" (the team dedicated to proactive security research) deemed Binder to be the most vulnerability-dense component in the entire operating system, with more CVEs per line than anywhere else.

That made it an obvious candidate for porting to Rust, Llamas said. Binder was the first user of Rust in the kernel, he added, although Ryhl did not publicly post the first version of what became the Rust implementation until 2023, well after the Rust experiment started in 2021. All told, the effort took more than five years. Binder is used for every single screen touch, permission check, and cross-application message on Android, which runs on more than three billion devices. In total, it works out to hundreds of billions of Binder transactions per second, globally, he added. That scale meant that even the smallest discrepancy between the interface provided by the C version and the one provided by the Rust version would cause problems and regressions for some use case.

One particularly tricky aspect has been performance, Ryhl said. Throughput doesn't matter that much; what matters is the tail latencies. Most screen frames on Android have a Binder transaction in the critical path of the frame, she explained. So, a difference of two microseconds on average is not a real problem, but if Binder is ever twenty milliseconds slower, even once in a while, people will notice and care.

The actual algorithms that the C and Rust implementations use are identical, she continued, so there are no large differences in throughput. But, because Rust handles locking differently, there were problems with the tail latency from lock contention that she had to debug. For example, one user-reported traceback showed Binder attempting to take a mutex that was held by another process. That process was preempted, and did not resume executing for twenty milliseconds, well past the sixteen millisecond budget to render a single frame.

It was a classic case of priority inversion. To solve the problem in Binder, Ryhl moved as many operations out from under the lock as possible, and was able to replace it with a spinlock, which made the problem go away. The equivalent lock in the C implementation was already a spinlock: "I deviated from C Binder, and pow. It has eighteen years of accumulated quirks."

Eventually, however, the Rust implementation was good enough for most use cases. And the C implementation was still producing new vulnerabilities every time someone tried to introduce a new feature. Eventually, Llamas and Ryhl decided to only add new features to the Rust implementation, in order to motivate people to switch and to avoid headaches from the C implementation. That policy has resulted in the Rust version becoming faster than the C version, because Ryhl was able to introduce an algorithmic improvement that reduced the number of needed system calls, a change that had been considered too complex for the C implementation. Now that the C implementation has been deleted, there are more of those coming, she promised.

Another area that proved difficult was dealing with tracepoints. Users aren't supposed to rely on the presence or behavior of most kernel-internal tracepoints, but they do. This meant that Ryhl had to copy the existing tracepoints in Binder as a de facto part of the driver's API. That even extended into some of the data structures involved in the driver. In one case, she said, there was a reference-counted structure that had a slightly different reference count in the Rust implementation, because the Rust code was holding an additional pointer to the structure. That turned out to be a problem for one particular piece of client code, since it relied on checking the reference count via a tracepoint in order to determine when the C implementation had reached a particular state.

There was also a lot of toolchain support needed, Ryhl continued. The Rust implementation had to work with kernel address-space layout randomization (KASLR), control-flow integrity (CFI), and profile-guided optimization. Production Android kernels are built with all of those enabled, and since they impact code generation, the Rust code needed to account for them.

Llamas then went into more detail about the deployment plan that will be used to convert users to the Rust implementation. A major problem with just rolling the Rust implementation out is the existence of vendor hooks: custom tracepoints used to inject vendor-specific behavior into the kernel. The Rust implementation of Binder was not able to reproduce those in every case, and therefore many vendors are stuck on the C implementation until they update their code. That's going to be a slow process.

Old stable versions of the kernel will continue to have the C Binder, and receive security fixes, which gives the various Android vendors a little bit of leeway until they're forced to update. After the conference, the patch removing the C implementation was merged as part of the 7.4 merge window, so that is the version past which the Rust implementation is required. 7.3 is the designated long-term-support release for 2026.

One person asked whether this would pose a problem for people compiling the kernel with GCC. Miguel Ojeda responded that many distributions are using a workaround for the current lack of Rust support in GCC: they are building the C side of the kernel with GCC, and the Rust side with LLVM. He said that he had advised against compiling the kernel in that way, because it is "a complete hack", though people who use it are unlikely to complain about being forced onto Clang. Greg Kroah-Hartman added that it will take months or years to learn about anyone who has problems with the Rust version of the driver, given how slowly Android vendors update their kernels. Furthermore, the removal is a single patch that can be cleanly reverted, if someone needs to continue using the C version.

Llamas thought that it was worth considering what the removal process should look like for other code that gets ported to Rust. He asked what people thought should happen to the C version of converted drivers on long-term-support branches. Ojeda said that the process would be exactly the same as the existing policy for replaced C code. The only difference between Rust and C in long-term-support releases is that the Rust maintainers backport fixes for soundness problems, he said. Kroah-Hartman told Llamas not to worry about code that has been replaced: "Just delete it. I take patches for subsystems that have been deleted. It's fine."

With that declaration, the session, the conference, and the presence of the C Binder driver in the kernel were all over. Binder is the first nontrivial component in the kernel to be ported to Rust, and its journey has revealed several pitfalls that don't apply to new drivers written in Rust from scratch. Still, the most difficult problems were not Rust-specific; they were the compatibility problems that any rewrite would face. Whether any other kernel components will find the hassle of a rewrite worth it, and how long they will take to accomplish it, remains to be seen.

Managing the kernel CVE flood

2026-11-05 00:00:00

by: Jonathan Corbet

By Jonathan Corbet

November 2, 2026
LPC
We recently looked at how the kernel community is dealing with the firehose of vulnerability reports, but said little about how users of the kernel are responding. At the 2026 Linux Plumbers Conference, Amazon employees Dylan Johnson and Justinien Bouron discussed the problem from the point of view of engineers trying to keep AWS running and secure in the face of a storm of CVE disclosures. The kernel community's longstanding advice is to run current kernels, and that turns out to work — sort of.

Bouron started by reminding the audience that the kernel community became its own CVE numbering authority (CNA) in 2024. The immediate result was the issuance of thousands of CVE numbers every year, forcing companies to rethink how they handle kernel vulnerabilities. The engineers running the AWS cloud were not immune to this change.

Triage

Linux, he said, runs everything from crock pots to nuclear power plants; each type of deployment has its own threat model and fault tolerances. The impact of any given CVE can vary considerably from one situation to the next. It is thus necessary to triage CVEs as they arrive, assessing the impact of each on a specific environment; nobody else can do that work for you.

After triage, the next task is to determine how to mitigate the threat, if any. One possible response is to do nothing, which may be fine when dealing with, for example, a CVE affecting an unused driver. The recommended approach, usually, is to wait for a new long-term-support (LTS) kernel, but that can leave systems vulnerable until that kernel has arrived, been tested, and deployed. Cherry-picking fixes can be faster, but has its own risks. In other cases, the best response may be to work around the issue in some way, perhaps by disabling the vulnerable code. The proper response has to be figured out for each incoming CVE.

Triaging of CVEs can help by speeding up the mitigation response, he said. Internal update schedules do not always align well with kernel-release schedules, or a new LTS update may arrive while the work to deploy the previous one is still underway. If that new update contains a fix for a severe vulnerability, it might make sense to cherry-pick that fix rather than going through the whole testing process.

Other times, there may be important vulnerabilities that are not fixed in the specific LTS kernel series that one is running. Fixes land in the mainline kernel first, and are subsequently backported to the stable releases. Backporting is relatively easy when the target is a recent kernel, but it becomes harder with older kernels. So the older LTS kernels will not receive all of the fixes that are applied to the mainline; the number of missing fixes grows over time. The 5.10.267 stable kernel, he said, has over 1,700 open CVEs, of which 1,200 are at least 90 days old. Most of those will probably never be fixed. Sites running 5.10 kernels thus have the unpleasant choice of remaining vulnerable or backporting the missing fixes themselves.

Backporting all 1,700 of those fixes is not possible, though; that is where the triage process comes in by helping to determine which patches merit that sort of effort. Before 2024, there were roughly two kernel CVEs issued every week, so a manual triage process was workable. After 2024, though, the rate went up to 16 — per day. And that was before the LLM-driven tsunami hit; now there can be hundreds of new CVEs showing up in a single day. At that rate, manual review simply is not possible.

So the triage process must be at least partially automated. The first step in that direction is "autopruning" — filtering out the CVEs that are not applicable to a specific kernel configuration. The CVE records issued by the kernel CNA include detailed JSON reports indicating which kernel versions and which files are affected. Filtering on those parameters allows about 70% of the CVEs to be discarded. This figure could probably be improved further by trimming down the AWS kernel configuration, which probably still enables a lot of unneeded features and subsystems. This trimming can be effective, but it is a difficult problem, requiring a detailed knowledge of the deployment environment. If one does not know about every use of the systems involved, it is hard to know what can be removed. There are over 32,000 configuration options for the kernel; playing with them is an easy way to create bugs or performance regressions that only show up months later. For environments running at a massive scale, the problem is almost impossible.

As the CVE rate increased, even the pruned stream involved far too much manual review. The solution chosen was, perhaps inevitably, to involve an LLM. This system is fed the pruned CVE stream, along with the active kernel configurations and threat-model documentation; it then generates a score for each CVE. The output is a table with a description of each CVE and a decision on whether (and how badly) it impacts AWS; it is meant to be a resource that humans can then quickly review. That review, he said, is now the only manual step in the whole process; it is the final bottleneck, and is hard to optimize further, but there is no desire to drop it and rely entirely on the automated system.

Is this system good enough to allow AWS to stick with older LTS kernels? No, he said, there are simply too many unpatched CVEs in those kernels, forcing sites to either accept vulnerabilities or backport fixes themselves. If the backport path is taken, the result is a kernel that nobody else has tested, meaning that even more in-house testing is needed before deployment. It is also necessary to be sure that the patched system is truly no longer vulnerable to the problem. Whoever does this work will have to contend with a lot of difficult conflicts that probably need subsystem expertise to resolve. For extra fun, the CVE reports may not list all of the patches needed to resolve an issue.

The end result, he said, is that this path is not sustainable; the model of following an older LTS kernel until it reaches end of life is obsolete. The only way to keep up with the stream of fixes is to upgrade to newer kernels.

Keeping up with stable

Johnson took over to talk about how those upgrades go. In late 2024, AWS was still running kernels from the 5.10 series and had to decide whether to upgrade. The lifetime of most stable kernels is two to three months he said, but it took AWS a full year to transition to a new kernel. Upgrading to a random stable kernel would result in deploying a kernel that had gone out of support long before, so the only viable approach is to stick with the LTS kernels.

Which LTS should be chosen when upgrade time comes? The newer LTS kernels are fixed more quickly and have less outstanding CVE debt — the number of unfixed CVEs grows more slowly with those kernels. The median time for a patch to land in 6.18, he said, is 18 days, while for 5.10 it is 32 days. Since maintaining LTS kernels is not easy, the newer ones tend to be prioritized; the backports to those kernels are easier. In other words, the newer LTS kernels are safer. Since they have fewer unfixed CVEs, newer kernels are much less likely to force the in-house backporting of fixes.

So upgrading to the latest LTS kernel is the best option. But it is still not easy. In 2021, the upgrade from 4.19 to 5.10 took about 24 months, much of which was spent forward-porting out-of-tree patches. For the upgrade to 6.12, that had been reduced to 12 months, and the upgrade to 6.18 only took six months. This upgrade time has been reduced through a combination of better tests and a more experienced team. An effort to reduce user-space dependencies has resulted in fewer regressions, which eases upgrades as well.

Every issue that came up in the upgrade to 6.12 was tracked; 45% of them turned out to be in the kernel itself, mostly in "a few hundred" out-of-tree patches. User-space problems accounted for 43% of the problems, configuration problems were 7%, and firmware-related problems were the remaining 5%. That last category is partly driven by improved error reporting for hardware problems, resulting in a higher error-detection rate. Of the kernel-space fixes, he said, 15% were submitted upstream (he did not say how many were accepted); the hope is for that number to increase over time.

Johnson provided a few examples of the types of problems that were encountered in upgrades:

  • The change within the memory-management subsystem from the virtual memory area red-black tree to maple trees made mmap() and munmap() operations slower. This problem was addressed by changing user space to perform fewer of those operations.
  • Switching from the completely fair scheduler to the EEVDF scheduler changed the timing of fork() operations. The completely fair scheduler prioritized the parent after a fork, and user space depended on the parent running first. Again, the solution was to fix user space.
  • The default value of max_sectors_kb was increased, leading to firmware timeouts. There is a great deal of hardware diversity in the AWS fleet, and some of that hardware did not react well to the larger size. Some tuning addressed this problem.

In conclusion, he said, Hyrum's Law applies here as everywhere else; every visible change will break something for somebody.

Eventually it would be good to get to a point where AWS is always running the latest stable kernel. With a six-month transition time, though, that is not yet possible. There is a need for better tooling and faster qualification of kernels. Even then, though, many problems turn up during the "soak time" while a new kernel is being tested; going faster risks missing those problems until after deployment. One way of improving the situation is continuously running the current stable releases in a testing environment, then switching to the next LTS kernel once it is available.

He concluded by saying that, until AWS could run the latest stable release, it would have to continue triaging CVEs. But perhaps even that will not be enough in a world where models can find and exploit vulnerabilities before a fix is made and a CVE issued.

Ben Herrenschmidt pointed out that the speakers worked on the hypervisor side of the AWS fleet, so they have a firm grip on everything that is running under their kernels. On the distribution (user) side, life is nowhere near as easy; there is no visibility into what features users need. One thing that might help, he said, would be to split the kernel's modules into separate packages, forcing a conscious decision before installing each one rather than just dumping 2,000 of them onto the system at once.

Thorsten Leemhuis asked why they don't test mainline releases rather than the latest stable updates. The answer was that the AWS upgrade process still is not fast enough to make that worthwhile, but it is the eventual goal.

The final question came from an audience member who said he works for Google and could have given the same talk. He asked how the LLM-based triage was evaluated, and what the results were. Johnson answered that the model makes bad decisions 5-10% of the time, so the human review step is definitely needed. Anybody developing such a model should plan on an extensive evaluation period before trusting it.

Plasma X11 session removal surprises some Fedora users

By Joe Brockmeier

November 4, 2026

The KDE Project announced, in 2025, that Plasma 6.7 would be the last version of the desktop environment that would support X11 sessions. Those who keep up with KDE's announcements no doubt expected it when Plasma 6.8 dropped X11 support as promised. What seems to have come as a surprise, at least to a number of Fedora KDE Plasma Desktop users, is that the Fedora 44 release—which shipped in April with Plasma 6.6—received an update to Plasma 6.8 that swept away the X11 session without much warning. Despite the surprise, it is gone for good: the Fedora Engineering Steering Committee (FESCo) has voted against a request to revert the update for Fedora 44 and the just-released Fedora 45.

Update

The cadence of Fedora Linux releases and Plasma releases do not line up particularly well. A new Fedora version is released roughly every six months, and supported until four weeks after the release of "Release N+2", or about 13 months. For example, Fedora 44 was released in April 2026, and will reach end of life about four weeks after Fedora 46 is released in April 2027. Feature releases of Plasma are released roughly every four months: 6.6 was released in February 2026, 6.7 in June 2026, and 6.8 in mid-October. Support for a feature release generally ends with the release of the next feature release, with the exception of long-term-support (LTS) releases; 6.6 is an LTS release and it is scheduled to receive support through February 2029.

Since the release schedules do not align well, and because the members of Fedora's KDE SIG do not want to attempt supporting multiple Plasma releases, its update policy is to maintain a single Plasma version across all Fedora releases. That means that a Fedora release is likely to see three Plasma feature releases during its lifecycle. This is somewhat unusual for Fedora; its stable-release policy says that "we should avoid major updates of packages within a stable release" and that software updates should "aim to fix bugs, and not introduce features".

There are exceptions to the policy, though, for certain packages such as the kernel, the Go toolchain, and KDE. As the KDE SIG's policy page notes, user-visible changes have slowed down with more recent Plasma 6.x releases. It's conceivable that many Fedora KDE users don't even notice that they have moved from one Plasma feature release to another.

6.8 update

When support for X11 went away, though, users did take notice. Tomáš Trnka asked "is there a compelling technical reason why the -x11 packages have to be obsoleted by 6.8, even on [Fedora] 44?" He wondered if the breaking change, in the middle of the lifecycle, had been communicated, and he had just happened to miss it—or if the obsolescence was an accident that just slipped into Fedora 44. "I would entirely understand that in F45 as a major upgrade often comes with forced feature retirement, but I certainly didn't expect a routine dnf upgrade on F44 to blow away the X11 session".

Adam Williamson asked Neal Gompa, a member of the KDE SIG and FESCo, if there had been a discussion about whether this was an appropriate update for a stable release that had shipped with X11 support. Gompa said that the X11 packages had been "expressly deprecated" and were expected to be removed as soon as support was dropped by KDE upstream. "Plasma X11 has also been unsupported since Fedora 40 when Plasma 6 was introduced." That was in 2024, when the KDE SIG not only dropped its support for Plasma sessions on X11, but attempted to block others from providing any X11 packages for Plasma. FESCo allowed packages that reintroduced X11 support in Fedora's repositories. Those packages, however, were not maintained by the KDE SIG. Since Plasma 6.8 is incompatible with X11 the kwin-x11 and plasma-workspace-x11 packages were obsoleted and removed by DNF when users upgraded to Plasma 6.8.

Another user, "ab cd", asked how they could get the X11 session back. "I know that Fedora hasn't officially supported X11 (with KDE) for a long time, but it worked fine, and now a number of things don't under Wayland." They wanted to know if there was any way to undo the update and keep X11 support. Allen Akin complained that "session restore still doesn't work, even for a few plain-vanilla Konsole windows", and that there were some glitches he had to work around due to having to switch from NVIDIA's proprietary drivers to the open-source Noveau drivers. He said he was thinking about switching distributions, or at least window managers, and that it was "unnecessary pain caused by poor release strategy".

Sérgio Basto asked FESCo to revert the changes for Fedora 44 and 45. FESCo member Timothée Ravier pointed to the earlier FESCo decision that allowed X11 packages but said that the KDE SIG "is not responsible for ensuring these packages adapt". Ravier said that it was not realistic to keep Fedora 44 on Plasma 6.7, since its end-of-life date is expected to be in January 2027, while Fedora 44 will be supported until June 2027. Maintaining 6.7 for Fedora 45 was "not even an option". He said that he was against Basto's request. He suggested that one option would be to maintain Plasma 6.7 and its dependencies in a Copr repository.

The FESCo decision that Ravier cited also said that the KDE SIG "should provide a notice before major changes". Steve Cossette had indeed sent a notice to Fedora's devel mailing list on October 21:

Despite the X11 subcomponents no longer being supported by the KDE SIG, an independent maintainer was offering those separately. These components remained deprecated in Fedora and were unsupported by the KDE SIG and now Plasma 6.8 no longer has the code for these components, so the Plasma 6.8 update will obsolete them on upgrade.

For users of the x11 components, we recommend you run `dnf offline-upgrade` or use Discover, as the update may break the system otherwise.

The reversion request was discussed and voted on during the FESCo meeting on November 3. FESCo rejected the request with eight members against; Zbigniew Jędrzejewski-Szmek cast a +0 vote. He said in the meeting that he thought the removal was unfortunate, and that the update "could have been dragged out a bit".

Happily for users, there are still quite a few desktops and window managers that support X11—but Plasma is no longer one of them. There is a fork of Plasma, called SonicDE, that preserves X11 support. It is packaged for quite a few distributions, but thus far there are no packages for Fedora from the project.

In hindsight, the Fedora Project and KDE SIG could have communicated the pending removal of Plasma's X11 support during the Fedora 44 release cycle a bit more explicitly. While some users might have anticipated the removal, or known about the exceptions to the Fedora stable update policy for KDE, it is not unreasonable for a user who installs a major operating-system release to expect a major feature to exist throughout the life of that release.

It also seems reasonable, though, that the KDE SIG is unwilling to go to great (or any) lengths to preserve Plasma X11 support once the upstream project has done away with it. The SIG made its position on X11 support clear years ago, and the clock has always been ticking.

The second part of the 7.4 merge window

2026-11-05 00:00:00

by: Daroc Alden

By Daroc Alden

November 2, 2026

The 7.4 merge window, which closed on November 1, included a record-breaking 18,591 non-merge changesets. That is almost as many as the entire 7.3 development cycle, which had 18,765, itself a record breaker. Of those, 11,838 landed after the article covering the first part of the merge window. Most of those were bug fixes of various forms; it seems as though bug fixes may be crowding out feature additions across the open-source ecosystem to some extent. Still, a good number of new features were included, and a handful removed, in the tail end of the merge window.

The most important changes included in this release were:

Architecture-specific

  • Super-H no longer supports NUMA or sparse memory. The sparse-memory support only provided an additional 128KB of memory on most systems (and 256KB on shx3), while complicating the kernel's general NUMA-handling code. Its removal decreases the size of a compiled kernel by almost enough to make up for the removal on its own.

Core kernel

  • The DAMON subsystem now supports additional DAMOS filters, including a filter for pages that are not access-idle and one for huge pages of a given size.
  • DAMON can also now track accesses to hugetlb-backed memory, which is expected to specifically help machines running guest VMs on hugetlb-backed memory.
  • DAMON target metric flags (which determine which memory metrics DAMON will attempt to keep within the configured bounds) can now be inverted, which allows the existing metrics for active memory to also control the amount of inactive memory on the system. Every DAMOS filter can now be used in two ways.
  • The unused-huge-folio shrinker is now memory-control-group aware, which should prevent memory reclaim in one control group from causing the shrinker to break up folios in other control groups.
  • The BPF verifier can now use scalar evolution to understand more loops. Currently, support is fairly limited, but it should still make it much easier to write traditional loops and have them directly accepted by the verifier.
  • The new callx instruction allows BPF programs to make indirect calls to static BPF subprograms. Indirect call support has been on the roadmap for BPF for some time; it should make writing programs that are best expressed using function pointers much easier. In particular, this lays the groundwork for supporting Rust's implementation of dynamic dispatch.
  • Another Rust-friendly change is the addition of unwind_goto and unwind_exit, which allow Rust panics or C++ exceptions to be implemented correctly in BPF.

Filesystems and block I/O

  • A new DM_VERITY_VERIFY_ROOTHASH_SIG_FORCE configuration option forces dm-verity to validate signatures on a device. In kernels built with the option, it will no longer be possible to override dm-verity's signature-checking behavior from the kernel command line.
  • A set of long-awaited fixes make it much safer to use untrusted floppy disks.
  • User space can now control NFS's RPC registrations using a new set of flags. This change both allows a management daemon to have more control over NFS's setup, and prevents an unresponsive rpcbind process from stalling NFSD administration.
  • NTFS now supports stream operations for files that have associated named streams. The documentation explains how to use them correctly.
  • NTFS can also query file attributes, although there is no support yet for writing them. NTFS attributes are used to mark files as immutable, append-only, or not to be included in core dumps, among other things.
  • The ext4 filesystem has added support for buffered iomap access. The feature needs to be enabled using the buffered_iomap mount option, and the filesystem does not support online defragmentation, inline data, fsverify, fscrypt, non-extent inodes, or data journaling while the option is enabled. Despite those drawbacks, users may want the feature because it does make large writes much faster.
  • CephFS no longer supports inline data. This feature was never fully enabled, being considered experimental, and was officially deprecated in 2020, so hopefully nobody is relying on it.

Hardware support

  • Clock: Raspberry Pi 5 realtime clocks.
  • GPIO and pin control: Toshiba TC9563 embedded GPIO controllers, Qualcomm Hawi SoC TLMM and LPASS LPI TLMM pin controllers, Qualcomm Kuno SoC TLMM pin controllers, Qualcomm MSM8952 SoC TLMM pin controllers, Qualcomm PMAU0102 SPMIO GPIO controllers, Starfive JHB100 pin controllers, Ambarella CV75 GPIO controllers, Econet EN7528 controllers, Allwinner Sunxi A733 pin controllers, and Mediatek MT6735 pin controllers.
  • Hardware monitoring: Axiado AX3000 PWM fan controllers, AX3005 PWM fan controllers, AX3000/AX3005 TSADC controllers, Infineon TDA38740/TDA38725 power-monitoring buses, and MAX20826/MAX20855B/MAX20908/MAX20912/MAX20826/MAX20916 power-monitoring buses.
  • Industrial I/O: Analog Devices LTC3208 I2C LED drivers.
  • Miscellaneous: BCM2712 IOMMUs.
  • Networking: Qualcomm CSI2 C-PHY/DPHY devices.
  • Power: Texas Instruments bq27z746 power supplies, Texas Instruments bq28z620 power supplies, and AB8505 power supplies.
  • Sound: Qualcomm WCD9378 SDCA codecs, ESS ES9039Q2M codecs, Nuvoton NAU83G60 amplifiers, Senary SN624x SoundWire SDCA codecs, TI TAS2573 DSPs, and Pioneer DJ DDJ-SZ USB audio devices.
  • Storage: Apple M4 ANS2 NVMe drives.

Miscellaneous

  • The Moxa serial interface driver has been removed, given that no known hardware for it still exists and the company that produced it no longer uses the driver.
  • The C implementation of the binder driver has been removed in favor of the Rust implementation, which is now considered stable. Fixes for the C implementation should be sent directly to the relevant stable trees, given that it will no longer be possible to simply submit them to the mainline marked for backporting.
  • The CXL developers have started working toward support for devices with dynamic capacities, although more follow-up work is required before the code will be usable.
  • The I3C subsystem has added the core code needed to support I3C hubs, although drivers for particular hubs are still in progress.

Security-related

  • BPF security modules can now set a file's extended attributes when it is first created, eliminating a small window of opportunity during which programs could have seen the files without the necessary extended attributes.
  • User space now has a defined way to look up which keyrings are being used for fs-verity and dm-verity, rather than trying to read the information out of /proc/keys. In turn, that allows user-space processes with appropriate permissions to add keys to the keyring and seal it against further modifications.

Tools

  • The tools/mm/page_owner_sort helper, which is used to sort the output of /sys/kernel/debug/page_owner in order to debug which processes are causing pages to remain in memory, can now actually sort entries, along with having better filters and clearer documentation.
  • The rtla osnoise top command now accepts an --ipi flag to report the sources of inter-processor interrupts observed while tracing with the tool.
  • Ftrace can now report the maximum amount of time that a given function in the kernel took, in addition to reporting the average and variance.
  • The kernel's tracing subsystem can now be instructed to filter events based on whether they occur during the execution of a given function. So, for example, it is now possible to search for trace events that occur during calls to vfs_read(), or, alternatively, everywhere except calls to vfs_read().
  • The perf command now supports sampling x86 SIMD registers, performing weighted sampling, and separating out memory accesses by assigned memory range, among many other small improvements. The memory-range support, in particular, will help track which accesses go to persistent memory, high-bandwidth memory, CXL-attached memory, or any other special memory areas.

Virtualization and containers

  • Arm hosts now support pKVM state isolation, which protects a guest virtual machine's register state from being read by the host, except for what is necessary to handle a VM exit. This is part of a broader set of changes to enable confidential computing, although the work is still in the preliminary stages.
  • Hosts can also disable per-VM memory attributes. The main use for this is enabling in-place conversion between private and shared guest pages. The setting cannot be changed after KVM is loaded, so guests relying on pages remaining private can continue to rely on that behavior.

Internal kernel changes

  • The memory-management subsystem now uses per-VMA locks in all configurations. This simplifies a lot of the code around modifying memory areas, because developers no longer have to think about two separate locking schemes.
  • There are new Rust bindings for DMA fences. The bindings automatically enforce a number of rules that are required to use DMA fences correctly, which should make writing drivers that interact with them a bit less of a headache.
  • Checkpatch is now more aware of which code in the kernel repository runs in user space. A new --userspace option can also be used to force checkpatch to use the user-space rules, when some new user-space code is added.
  • The kselftests can now run on architectures without an MMU, which should help with embedded kernel development.
  • There were 202 exported symbols removed in this merge window, and 402 added; developers also removed one kfunc and added 58 others. See this page for the full list of changes.

The changes in 7.4-rc1 were contributed by 2,678 developers, 625 of whom were first-time contributors. Now comes the stabilization period, during which bugs are found and fixed before the release of the 7.4 kernel. At the time of writing, Linus Torvalds is still considering a few pull requests which he may bring into the -rc2 release. The release date of the 7.4 kernel is somewhat flexible, but can probably be expected around December 21. If the recent pattern of ever-growing numbers of bug fixes holds, we can probably expect more than 3,000 commits to find their way into the kernel by that time.
